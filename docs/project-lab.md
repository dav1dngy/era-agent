# ERA Project Lab

Project Lab lets ERA work on **external software that you are authorized to work
on**: review it, modify it, or reconstruct selected functionality of a reference
application. It is separate from the [Improvement Lab](improvement-lab.md),
which improves ERA itself. Project Lab never operates on ERA's own installation
(paths inside it are refused).

> Status: ERA v0.2.0, experimental.
> The automated tests use scripted *mock* agents, real REA and the projects' own
> tests. Real Codex runs (including one end-to-end modify, one screenshot rebuild
> and a review) are recorded in [provider-validation.md](provider-validation.md);
> Claude Code has never been run against the real CLI. See
> [project-lab-testing.md](project-lab-testing.md) and
> [SUPPORT_AND_VALIDATION.md](SUPPORT_AND_VALIDATION.md) for exactly what is real,
> mocked and unverified, per revision.

## The three modes

| | Review | Modify | Rebuild |
|---|---|---|---|
| Input | an external project (`source`) | an external project + a task | an authorized reference artifact + a task |
| Output | prioritized findings with evidence and locations | a verified, reviewable diff | a new independent project + comparison report |
| Changes the original? | never | only after your approval, as a reversible patch | never touches the reference; writes the new project to an empty `destination` only after approval |
| Coding agent | optional, read-only | required (or you edit by hand: `manual`) | required (or you implement by hand: `manual`) |
| Uses REA | JavaScript projects (application graph) | JavaScript projects (analysis feeds the plan) | the reference: Mach-O, JavaScript apps, archives |

```
era project create demo --source ~/code/shop --mode modify --task "Fix the cart total" \
    --test "npm test --silent" --accept-fail "node --test acceptance/cart.test.js" --agent claude-code
era project modify demo          # isolated change, tests, regression check, diff
era project show demo            # the report
era project approve demo         # asks for confirmation, then applies the verified diff
era project rollback demo        # undo
```

## Workflow

```
Target selection → Capability detection → Baseline analysis → REA / source analysis
  → Implementation plan → Isolated modification → Automated testing → Regression evaluation
  → Human review → Approval
```

1. **Detection** reads the project's files: languages, frameworks, package
   managers, test frameworks, and build/test command *candidates* (used only when
   you did not configure commands, and only if the tool exists).
2. **Isolated working copy.** The project is copied (without `.git`,
   `node_modules`, build output; symlinks leaving the tree are skipped) into
   `<state>/projects/<id>/work/<run>/` and becomes its own git repository with a
   `baseline` commit. Git and non-git sources behave the same. Every change is a
   diff against that baseline.
3. **Baseline.** Build, test and acceptance commands run on the unmodified copy.
   Test output is itemized (TAP, node spec, pytest, go, cargo formats). Acceptance
   commands marked `baseline: fail` must actually fail, or the run stops *before
   any agent is paid for*: the criteria would not discriminate.
4. **Analysis.** JavaScript projects are analyzed with REA through ERA's
   byte-bounded pass planner; every project gets language-agnostic static checks
   (secrets, risky calls, TODOs, very large files, missing tests). Findings carry
   severity, evidence and file:line locations.
5. **Plan** (Modify). Generated by ERA from the task, the analysis and the
   baseline, with "likely relevant files" derived from the task text and failing
   output. It is the agent's brief, not a prediction.
6. **Implementation.** A configured coding agent works in the copy (see below).
   Up to `limits.maxAttempts` attempts; after a failed attempt the next prompt
   carries the failing commands' output.
7. **Verification and regression detection.** Build, tests and acceptance commands
   run again. The guards are applied to the working copy **after** those commands
   ran, because they run inside it and can change it; the decision is bound to the
   hash of exactly that diff. A change passes only if: files changed, no protected file changed,
   limits respected, the build did not break, no test that passed at baseline
   stopped passing **or stopped being listed** (deleted tests are a regression),
   and every acceptance command passes. Edited or deleted existing test files are
   flagged in the report.
8. **Review and approval.** The run stops at `awaiting-approval` with a report and
   a diff. `era project approve` shows the diff stat and asks for confirmation (a
   terminal, or `--yes`).

### Approval and rollback

* Approval binds to what was verified: the working copy must still produce the
  identical diff (SHA-256) and the original must be byte-identical to when the run
  began. Otherwise approval is refused and you re-run.
* **Modify**: the diff is applied to the original with `git apply` (after a
  `--check`). **Rollback** reverses the same patch, and refuses if you edited the
  touched files since (your later edits are never overwritten).
* **Rebuild**: approval copies the new project (without `.git`) into the empty
  `destination` and records a complete manifest of what was written (every path, nothing
  excluded). Rollback deletes the destination only if it still matches that manifest file for
  file; if you added, removed or changed anything, including inside `.git`, `build` or
  `node_modules`, it refuses, names the paths and deletes nothing.
* Review runs change nothing and need no approval.

### Rebuild prerequisites

Before a Modify or Rebuild run, `era project check <id>` (and Studio's checklist) lists everything that
could stop or weaken it, each with a fix; starting is refused with the whole list:

* a coding agent is installed and signed in, and supports images if you give screenshots;
* a spending cap exists, or unmetered agents are explicitly allowed;
* consent for each remote provider, and (Rebuild) your authorization statement for the reference;
* acceptance checks or behaviors to compare, because nothing is accepted without them;
* for Rebuild, an **empty** destination folder outside the project;
* a sandbox for running commands (macOS), or Trusted execution / `--trust-project` if you accept running them unconfined;
* for screenshot references, an offline renderer for the visual comparison.

Rebuild reconstructs *stated* behavior of a reference you are authorized to analyze; it does not prove equivalence.

## Isolation

| Concern | Control |
|---|---|
| Original project | Never written by any operation except `approve`/`rollback`. A content digest is checked at the end of every run; a difference marks the run failed with `ISOLATION VIOLATION` |
| ERA itself | Source, reference and destination inside ERA's installation are refused (symlinks resolved). All git commands for a working copy run with `GIT_CEILING_DIRECTORIES`, so git can never reach another repository |
| Project code (build, tests, acceptance, rebuilt behaviors, the reference executable) | Run in the macOS sandbox: no network, writes only to the working copy and a private temp dir, no signalling of other processes, no reads of ERA's state, of other projects or of the home directory and shared temp folders (toolchains on `PATH` and the working copy stay readable), secret-free environment. Without a sandbox they run only for `trust_project: true` / `--trust-project` |
| Coding agents | `command` agents are confined the same way, except that they may use the network and keep their environment. `claude-code` and `codex` run with their own permission models (Claude `acceptEdits`, Codex `workspace-write`; **read-only** modes during Review). They are not sandboxed by ERA |
| Several projects | Separate state directories, separate locks, separate ledgers |
| Prompts | Project content is treated as untrusted data and the prompts say so; prompts and agent output are redacted for secret patterns before storage |

## Coding agents, budgets and limits

* `agent`: `manual`, `command` (+ `agent_command`), `claude-code`, `codex` (same
  adapters as the Improvement Lab). `manual` pauses the run (`awaiting-implementation`):
  you edit the working copy, then `era project resume`.
* Spending: `limits.maxCostUsd` per run and `limits.maxCostUsdTotal` per project,
  both capped by hard limits; a metered agent receives the remaining budget
  (`--max-budget-usd` for Claude Code). Agents that cannot report cost (`command`,
  `codex`) are refused unless `projectLab.budget.allowUnmeteredAgents` is true.
* Time: `limits.commandTimeoutMs` per project command, `limits.agentTimeoutMs` per
  agent call; process groups are killed on timeout; a watchdog bounds every child.
* Project Lab refuses to run in CI environments.

## Cancellation, interruption and recovery

* `era project cancel <id>` stops a running operation (SIGTERM; process groups
  killed), removes the working copy and keeps the run record.
* A killed process leaves the run `interrupted` (detected through the project lock).
  `era project resume <id>` continues from the last finished step: finished steps
  (baseline, analysis, completed attempts) are not repeated.
* Failed runs (for example an unreachable agent) are resumable once the cause is fixed.

## REA's role

* Review/Modify: REA analyzes JavaScript application structure (modules, imports,
  externals); unresolved local imports are confirmed against the filesystem.
  Python, Go, Rust, Java and other projects get no REA evidence (REA's source-level
  workflows do not cover them), and the report says so.
* Rebuild: REA analyzes the reference (Mach-O structure and Hopper decompilation of
  exported functions where available, JavaScript apps, archives). **Behavior is
  captured by running the reference in the sandbox** (exact stdout and exit code),
  not through REA's PTY capture. The implementer receives a *specification*: stated
  behaviors, observed structure (names, imports, call edges, dependencies), unknowns
  and assumptions. It does **not** receive decompiled code, strings or the reference's
  path. For directory references, near-verbatim copying (3+ long identical lines) is
  rejected. ERA cannot stop an agent from reading files elsewhere on your machine;
  the clean-room property depends on the agent honoring the prompt.
* Rebuild does not recover source code and claims no support for arbitrary formats.
  Only behaviors you list (stated or captured from the reference) are checked.

## Where state lives (and how ERA Studio can use it)

Everything is plain JSON/JSONL under `<stateDir>/projects/<id>/`:

```
project.json            configuration, status, approval
ledger.jsonl            events: run-started/finished, implementer-started/finished (with cost),
                        project-approved, project-rolled-back, isolation-violation, ...
runs/<run>/run.json     steps, results, attempts, status
runs/<run>/report.md    rendered report; plan.md, SPEC.md, change.patch, prompts/, agent/
work/<run>/             isolated working copy (removed on cancel)
```

The CLI is a thin layer over `src/project_lab/lab.js` (`ProjectLab`: `create`,
`list`, `status`, `show`, `review`, `modify`, `rebuild`, `resume`, `approve`,
`cancel`, `rollback`, `remove`). It takes injected dependencies (`config`, `rea`,
`log`, `createAgent`), returns plain objects, and every CLI command supports
`--json`. A graphical application can call the class directly or poll
`era project status <id> --json` and tail `ledger.jsonl`. No part of Project Lab
depends on a terminal except the approval prompt.

## Limitations

* macOS-focused: the sandbox exists only there. On Linux project commands need
  `--trust-project`, and agent isolation is detection-only.
* Real agents untested here: the `claude-code` and `codex` adapters are exercised
  against fake CLIs and, in Project Lab, against scripted mock agents only.
* Dependencies are not installed (the sandbox has no network): projects whose tests
  need `node_modules` or similar must already have them or be run with
  `--trust-project`.
* Findings from static checks are heuristics; agent findings are accepted only when
  they point at real files, lines and quoted code, but a finding can still be wrong.
* Test-output itemization covers common runners; otherwise regression detection falls
  back to exit codes.
* Single project operation at a time; no remote or team features; approval is a local
  acknowledgement, not an authenticated identity.
